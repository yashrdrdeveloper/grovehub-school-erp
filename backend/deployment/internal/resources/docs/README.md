# Multi-project deployment (migration)

Platform: 8080 private; School: 8081 private behind School ingress; Internal Tool: 8082 private behind its own ingress; Swagger: 8090 development only. Use independent credentials for each project and separate PostgreSQL databases. Existing Platform DATABASE_URL and AUDIT_DATABASE_URL remain authoritative. School and Internal Tool open independently owned pools at startup using SCHOOL_DATABASE_URL and INTERNAL_TOOL_DATABASE_URL respectively. Internal Tool has explicit business migrations; School has an explicit registry migration. The nginx example is not a complete TLS configuration. No production deployment is enabled by this change.

Generate local School workload credentials from `backend/projects/school` with `GOWORK=off go run ./cmd/workload-config /absolute/path/to/new-private-directory`. Source the resulting platform.env in the Platform process environment and school.env in School's process environment. Never commit these files. The generator creates independent forward and reverse workload keys, enables mandatory tenant access verification, and intentionally grants no global Foundation access. Register canonical School UUIDs and align Identity tenant IDs before login. School readiness checks its database and Platform readiness; it does not validate every workload grant.

## Database provisioning

Provision separate databases and login roles for Platform, School and Internal Tool; a shared PostgreSQL server is acceptable. Revoke CONNECT from PUBLIC on each project database and grant it only to its owner and explicitly authorized migration roles. Use non-superuser application roles without CREATEDB, CREATEROLE or membership in another project's roles. Keep each process's environment isolated. Platform continues to use DATABASE_URL (and optional AUDIT_DATABASE_URL); consumers must not receive either. School and Internal Tool require PostgreSQL URIs with explicit host, database and user; use TLS for remote servers. The pool verifies the connected database and user against the URI, but separate environment values alone cannot enforce server-side privileges: verify ACLs during provisioning. /health/database is a private dependency probe, not application readiness. No database is created or migrated automatically.

## Build ownership

No root Go workspace is required. The Platform, School, Internal Tool, Core and Platform shared-library modules build with GOWORK=off. The Platform project requires `grovehub/libs/platform` using a checkout-relative replacement for `backend/libs/platform`. Platform annotation generation remains provider-owned and consumes Core through a local module replacement; School and Internal Tool generate SDKs from service-owned specifications. The local replacement is an intentional monorepo development dependency, not a published release. Each project can be built and tested via its own entrypoint. Root Makefile convenience commands do not share database credentials or start another project's process. Frontend package-manager files are scoped to frontend/. Published Core and npm packages, remote dependency verification and separate deployable repository checkouts are not yet complete.

## CI deployment artifacts

The existing project CI workflows package five independent Linux amd64 build outputs after their applicable tests/build checks: platform, school-backend, internal-tool-backend, school-frontend, internal-tool-frontend. Each GitHub Actions artifact is named with the exact commit SHA and contains a tar.gz plus an outer SHA-256 checksum. Each archive contains manifest.json, SHA256SUMS and payload/. Verify the outer checksum before extraction and run sha256sum -c SHA256SUMS inside the extracted directory. Backend payloads contain only the executable; frontend payloads contain only the static dist assets. Database migrations and server configuration are separate deployment steps. No env files, database credentials or signing keys are packaged. CI does not publish registry libraries, push production images or deploy to a server. Deployment approval and actual host provisioning remain separate work.

## Host installation and activation (Linux amd64)

These are deployment templates, not an executed deployment. Provision PostgreSQL and NATS separately. Create non-login users/groups gh-platform, gh-school-backend and gh-internal-tool-backend. Install the matching unit files from systemd/ into /etc/systemd/system and run systemctl daemon-reload. Install environment files as root:root mode 0600 in a root-owned mode 0700 /etc/groovehub. Each unit has an isolated StateDirectory; the release tree is root-owned and read-only to application users. The fixed loopback port is enforced by ExecStart. Never reuse workload private keys or database passwords between projects. Configure exact HTTPS allowed origins. For Internal Tool, provision network or identity-aware ingress restriction in addition to application login. Do not publicly expose ports 8080–8082, PostgreSQL, NATS or Swagger.

Install Nginx snippets in distinct TLS virtual hosts, supplying real certificates and hostnames. The School virtual host routes only its public/protected routes to port 8081; Internal Tool routes only its public/protected routes to port 8082. Neither exposes Platform. Run nginx -t before reloading. TLS, DNS, network restrictions, rate limiting and real host configuration are operator responsibilities. Both snippets serve versioned frontend static content from the current symlink.

Download an artifact from the approved CI run, confirm the expected commit and obtain its SHA-256 through a trusted release record. Checksums detect corruption, not malicious replacement of the artifact and checksum together. From a root-controlled copy of this deployment directory, activate one project at a time:

    sudo bash scripts/deploy-release.sh school-backend COMMIT TRUSTED_SHA256 /path/to/school-backend.tar.gz

The verifier rejects path traversal, duplicate entries, links, special files, unexpected files and checksum/identity mismatches. It creates a new immutable-by-convention root-owned release directory and switches only that project's current pointer. Activation restarts the corresponding service and checks full readiness. If a gate fails, the previous pointer and service active/stopped state are restored; old application health still needs checking. Frontend activation validates nginx configuration and the matching private backend's health, not a full public browser transaction. To roll back manually, invoke the same command with the original approved artifact and its commit/digest. Keep prior artifacts and compatible database migrations. This is binary/static rollback, not database rollback.

Normal activation checks dependency readiness: Platform checks both PostgreSQL pools, broker health and Audit readiness; School checks its owned database and Platform /ready; Internal Tool checks its owned database, exact schema version, an active L2 operator and Platform /ready if its optional catalog adapter is enabled. These are availability checks, not end-to-end authorization or browser checks. Health endpoints remain private. The explicit --staging flag checks liveness (and consumer database probes) only; never use it for production. Platform handles SIGTERM/SIGINT with graceful HTTP shutdown before closing dependencies.

## Explicit database migration using packaged binaries

No Go toolchain or separate SQL checkout is required for the embedded migration commands. First prepare a verified release without switching the current pointer or starting services:

    sudo bash scripts/deploy-release.sh platform COMMIT TRUSTED_SHA256 /path/to/platform.tar.gz --prepare-only

With the previous application stopped or the migration independently verified to be backward-compatible, run the staged executable using a dedicated systemd transient unit and a root-owned migration environment file. The migration environment must target only the appropriate database(s), with credentials scoped to schema changes. For example (replace COMMIT and provision the env file first):

    sudo systemd-run --wait --pipe --collect --property=User=gh-platform --property=Group=gh-platform --property=EnvironmentFile=/etc/groovehub/platform-migration.env /opt/groovehub/platform/releases/COMMIT/payload/platform migrate all

Platform already embeds Foundation, Infrastructure, Integration, Identity and Audit migrations and uses the existing Goose histories. Internal Tool now embeds its existing explicit migration and bootstrap command in the deployed executable:

    sudo systemd-run --wait --pipe --collect --property=User=gh-internal-tool-backend --property=Group=gh-internal-tool-backend --property=EnvironmentFile=/etc/groovehub/internal-tool-migration.env /opt/groovehub/internal-tool-backend/releases/COMMIT/payload/internal-tool-backend migrate

Prepare the Internal Tool release using its own commit and digest first. Bootstrap the initial L2 using the same executable with bootstrap EMAIL and a password supplied on stdin (never argv or a committed file), using the appropriate Internal Tool database environment. School embeds its registry migration: prepare the school-backend release and run its executable with migrate, using a dedicated SCHOOL_DATABASE_URL migration environment. Register the existing canonical school UUID/code/name using register-school UUID CODE NAME before configuring directory access. No migration is run by activation. After successful migration and initialization, rerun deploy-release.sh without --prepare-only to activate. Database grants, backup/restore, cross-version migration compatibility, service runtime behavior and public HTTPS end-to-end still require host validation. A failed migration must be investigated before activation; application rollback never reverses schema changes.


## Centralized Internal Tool audit (optional)

Apply Platform Audit and Internal Tool migrations from the same approved release before activating. Configure independent OperatorAuditKeys on Platform and INTERNAL_TOOL_AUDIT_ORIGIN, INTERNAL_TOOL_AUDIT_KEY_ID, INTERNAL_TOOL_AUDIT_PRIVATE_KEY on Internal Tool. Local workflow events and their durable outbox are committed atomically. Existing workflow events are backfilled with stable occurrence UUIDs. The relay writes only through the Audit-owned restricted API using its generated SDK. The global operator ledger is separate from tenant search. No direct cross-project database access or browser-visible ingestion is introduced. Optional relay failures do not block local transactions; inspect pending/blocked rows and logs. Centralized delivery readiness, backlog alerting and operational reconciliation are not yet included.

The School registry lookup route is private and explicitly denied by the public Nginx snippets. Configure School registry reader public keys and Internal Tool directory private credentials independently; do not expose the restricted endpoint through the public virtual host. Deploy the School registry migration before enabling the reader. Verify canonical UUID alignment with existing tenant data; registration does not provision Identity accounts or tenant memberships.

School rename is opt-in: apply School registry migration 2 before provisioning the dedicated SCHOOL_REGISTRY_RENAME_KEYS public keys and matching registry.rename Internal Tool grants. The directory origin and rename origin must match. No browser route or production key is configured by the repository change. School-local rename receipts are not centralized yet.

For versioned school mutation receipts, deploy the Platform Audit receipt migration before School registry migration 4. Register a new rename template revision with expectedVersion (integer). Configure the optional SCHOOL_RECEIPT_* single-school publisher and matching independent Platform SchoolReceiptKeys. Receipt metadata is centralized, while actual old/new names stay in the School-owned immutable receipt. Unconfigured schools retain their local pending deliveries. External notifications and centralized receipt search are not provisioned. No deployment is performed by CI.

For multiple School receipt publishers configure SCHOOL_RECEIPT_PUBLISHERS instead of the legacy single-school values. Each publisher uses a separate school-bound credential. Monitor the private School GET /health/audit-delivery separately from application readiness; it detects blocked, aged and unconfigured pending receipts. The optional global L2 receipt search needs INTERNAL_TOOL_RECEIPT_READ_* and matching Platform SchoolReceiptReadKeys. This is explicitly global metadata access for L2, not a tenant-facing API. Actual school names are never replicated in the central receipt. External alerting remains unprovisioned.

School registry migration 5 introduces versioned status transitions. Provision independent SCHOOL_REGISTRY_STATUS_KEYS public keys and matching registry.status Internal Tool grants only after migration. Disabled schools can be selected only for lifecycle grants when directory resolution is configured. These historical registry-only changes are superseded by the generation-based suspension described below.

Deploy Audit migration 202611280004 before School registry migration 6. Configure SchoolStatusReceiptKeys and separate status publisher entries in SCHOOL_RECEIPT_PUBLISHERS. The prior rename-only search is replaced by /audit/restricted/school-mutation-receipts/search and /internal/protected/school-mutation-receipts/search; update SchoolReceiptReadKeys scope to internal.audit.school.mutation-receipt.read explicitly. Combined L2 history includes RENAME, ACTIVATE and DISABLE. Previous rename publishers retain their existing scopes. Generation-based tenant suspension is described below.

## Tenant access enforcement

Apply School registry migration 7, Identity session and password-token generation migrations, and the Integration OAuth-state generation migration before starting the new release. Configure PLATFORM_TENANT_ACCESS_ORIGIN, PLATFORM_TENANT_ACCESS_KEY_ID and PLATFORM_TENANT_ACCESS_PRIVATE_KEY. The installed Platform systemd unit requires PLATFORM_TENANT_ACCESS_REQUIRED=true; missing verifier configuration prevents startup. Provision matching SCHOOL_REGISTRY_ACCESS_KEYS public keys (issuer/subject platform-tenant-access, audience school, only platform.school.access-check, no delegation). The local credential generator provisions this pair automatically.

All Identity tenant IDs must match canonical School registry UUIDs. Platform verifies the live registry for login, refresh, actor-bound restricted routes and internal Identity authorization, recovery, onboarding, invitation delivery, Integration OAuth callbacks, provider operations, push processing and watch renewals. Disable increments the generation; old sessions and credential proofs never become valid again after activation. The Identity reconciliation worker durably revokes stale unexpired sessions. Legacy generation-zero credentials require fresh issuance. Disabled schools' existing mailbox connections are paused rather than deleted. Registry failures deny interactive access and defer retryable background activity. Logout/revocation remains independent of registry availability when a valid local session can still be resolved.

Foundation person records are global, not tenant-owned. The separate school-foundation workload is intentionally not generated or granted to ordinary School clients. Do not provision global Foundation grants for tenant-facing applications. Account-linked people have a restricted Identity profile read and a protected School wrapper, authorized by AccountView and the existing Identity account-to-tenant/person relationship. Only names and the person reference are returned. Student/guardian memberships and global person mutations remain separate future use cases. Internal Tool operator audit and registry lifecycle credentials remain independent and must continue to operate for disabled schools.

No distributed transaction spans School and Platform; requests already in flight and provider operations already accepted cannot be recalled. The restricted access-check client uses signed transport and a fixed route. Unconfigured isolated development remains compatible, but deployed services require the verifier.

### School mutation history filters
The L2 Internal Tool receipt history supports optional canonical school UUID and RENAME/ACTIVATE/DISABLE filters. Apply Audit migration 202611280005 before rollout and regenerate the Internal Tool audit SDK from the updated Platform contract. Filtering happens on the central immutable ledger before pagination. The existing dedicated receipt-reader credential and L2-only access are unchanged. History shows delivered mutation receipts, not pending approvals or undelivered events. Receipts carry no environment field, so selecting a school from any environment filters by its UUID only; it does not assert environment-specific history.

### Cross-project lifecycle verification
The Cross-project school lifecycle workflow provisions three isolated databases and builds the School executable and the Internal Tool workflow test driver independently. The Platform integration harness runs the real gateway, Identity auth/recovery services, Integration module and Audit receipt ledger. It exercises approved disable/reactivate operations, denies old sessions and credential proofs, checks unrelated-school isolation, runs durable session reconciliation and simulates a lost receipt acknowledgment to verify replay deduplication. The message broker is replaced by an idle test implementation; external email providers are not contacted. This complements the separate provider, authorization, PostgreSQL and frontend test suites. It does not constitute a production deployment.

### Resource budget and database indexes
Platform's business pool defaults to 20 open and 5 idle connections. An explicitly separate Audit pool defaults to 5 open and 2 idle. Override with PLATFORM_DB_MAX_OPEN, PLATFORM_DB_MAX_IDLE, AUDIT_DB_MAX_OPEN and AUDIT_DB_MAX_IDLE (1–100 open; 0–open idle). Invalid settings fail startup. School and Internal Tool retain 10 open and 2 idle each. Default total is 40 open connections when Audit shares Platform's pool or 45 when split; account for other clients, migrations, replication and PostgreSQL reserved connections. These are capacity limits, not measured throughput.
Apply Identity 202611280003, Integration 202611280002 and Audit 202611280006 before rollout. Indexes target tenant/session reconciliation, pending invitations, live proof invalidation, mailbox lookup, OAuth state cleanup and filtered receipt order. Validate with EXPLAIN (ANALYZE, BUFFERS) on representative staging data; index creation takes write locks, so schedule migrations appropriately. Gmail watch renewal runs immediately and advances a bounded keyset page every five minutes, retrying failures on subsequent sweeps rather than starving later connections. Registry tenant IDs accept canonical non-nil UUIDs; Platform-created person and connection IDs remain UUIDv7.

## Release acceptance checklist

Before promoting this development branch, require green workflows for the same commit: Cross-project school lifecycle, Backend annotation build, Independent project backends, Shared library release candidates, Deployment configuration, and both frontend builds (run manually when path filtering omits them). Verify generated API clients correspond to that commit. The School ingress forwards Authorization only on the four recovery/invitation validation/exchange paths; all other browser API routes strip it and all routes strip X-GH-Identity-Proof. CI tests the actual Nginx routing with a disposable upstream.

On the target host, complete these operator-owned gates:

- Verify database role isolation, PostgreSQL connection budget, available disk, NATS storage limits and backup retention. Restore a backup into an isolated database and record recovery duration before destructive migrations.
- Prepare all five verified artifacts, apply the owning database migrations, register canonical School IDs and bootstrap authorized operators. Provision independent workload keys, TLS and private ingress; do not reuse development keys.
- Verify private readiness of each application and the audit-delivery health of School and Internal Tool. Exercise login, recovery, approved lifecycle operations and receipt search over the configured HTTPS ingress using disposable accounts. Verify disabled tenants and unauthorized scopes cannot access restricted routes.
- Measure query plans and p50/p95 latency under representative school traffic, connection utilization and worker lag. A school-size estimate or successful build is not a load-test result.
- Validate provider OAuth and email delivery with a controlled test mailbox. The CI lifecycle suite deliberately does not call external providers or exercise production NATS.
- Record trusted artifact digests, migration versions, rollback compatibility and operator sign-off. Do not activate production if any applicable gate fails.

No production host, live database, OAuth account or backup destination was provisioned by repository changes. Publishing independent libraries and splitting repositories, if desired, require a separate release decision; the existing monorepo packages independently deployable applications.
