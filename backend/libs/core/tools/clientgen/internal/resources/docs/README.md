# Consumer-local API clients

Use the pinned OpenAPI Generator CLI adapter to generate Go clients from a service-owned versioned OpenAPI specification. Run `generate.sh SPEC OUTPUT_DIR PACKAGE_NAME` with Docker available and the image pre-pulled. Output must be a fresh directory within the consumer project. Review generated changes before replacing an existing client.

School's `make generate-clients` generates Audit, Identity, Foundation and Integration SDKs from the canonical specifications under `backend/projects/platform/services/<service>/internal/resources/api/openapi/v1/openapi.yaml`. Do not copy those specifications into consumer projects. Outputs are cached against the source specification and generator script. CI builds and tests the consumer with `GOWORK=off`.

The consumer injects its Core workload HTTP client into generated configurations. Only the route-selected identity proof may cross that boundary; never forward browser cookies or arbitrary incoming authorization headers. Preserve raw response bytes, status and permitted cookies at School ingress, and enforce response limits before SDK decoding.

Audit search and all 18 Identity authentication operations are wired to generated SDK methods. Identity account setup is password-only, and grant and session-revocation schemas reflect the actual controller DTOs. All 30 School Identity Account/RBAC/Capability/Approval business routes now select generated operations and decode generated request models. For these business operations the original JSON is deliberately preserved before workload signing, so SDK normalization cannot drop unknown fields, explicit nulls, empty arrays or 64-bit versions before Platform validates them. This is a wire-parity bridge, not complete typed serialization. Account and approval creation forward only the explicitly allowed Idempotency-Key header. The 12 allowlisted Integration business wrappers and the OAuth callback now use a dedicated generated Integration client; the generic HTTP forwarding adapter has been removed. Mail send is served by the generic registered provider action, not a separate School route. Gmail push remains provider-only ingress and must not be exposed by a School workload. Foundation has no School business use case or workload scope at this stage; its five restricted operations remain available to authorized Platform consumers through the existing annotation-generated person client. SDK generation alone does not grant access. School shares the service-neutral internal/platformhttp transport for bounded response handling, route-selected proof and wire-parity preservation. Integration regression tests cover all allowlisted operations, OAuth state and credential isolation. Generated authentication regression tests cover operation paths, proof forwarding, cookie preservation, error responses and invalid session IDs; CI must pass before marking the migration verified. OpenAPI 3.1 nullable/union and PATCH omission semantics require explicit compatibility tests. Infrastructure still needs a service-owned contract if it exposes cross-project HTTP operations. The adapter does not yet automate annotation-to-spec generation or @Client integration.
