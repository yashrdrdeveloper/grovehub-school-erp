# Internal Tool backend

Independent operator identity, approvals, API templates and execution. No School session reuse or direct Platform database access.

Set INTERNAL_TOOL_DATABASE_URL and INTERNAL_TOOL_ALLOWED_ORIGIN. Provision a separate non-superuser database role. Run make migrate explicitly before startup. Bootstrap the initial L2 once using a password of 12–256 bytes; pipe it from a secret manager or use a shell's silent read, e.g. bash: read -rs OPERATOR_PASSWORD; printf '%s' "$OPERATOR_PASSWORD" | make bootstrap-operator EMAIL=operator@example.com; unset OPERATOR_PASSWORD. Do not pass a password via argv or commit it. Migrations do not create accounts.

Operator login, me and logout are exposed at /internal/public/auth/login and /internal/protected/auth/{me,logout}. Session and CSRF cookies use the distinct __Host-gh_internal_* namespace, Secure and SameSite=Strict. Use HTTPS ingress (localhost development behavior depends on browser). Operator sessions expire after eight hours; logout revokes the stored digest. Login has a persistent per-email attempt budget and bounded Argon2 concurrency. Configure ingress rate limits and periodic cleanup of expired sessions and old attempt records before deployment.

GET /health/database checks the owned database; /health/ready requires the owned database, current schema, an active L2 and Platform readiness when the catalog adapter is configured. L1/L2 are the initial personas; L2 can register, list, activate and disable operators. Platform execution credentials are optional and catalog-only.

## Registry and approval workflow

Migration 2 creates environments, immutable template revisions, approval requests and append-only application workflow events. L2 creates logical environment codes and template revisions; no URLs or credentials are accepted for environments. Templates contain restricted endpoint patterns, GLOBAL/SCHOOL scope, bounded recursive input schema (string, integer, number, boolean, object, array, nullable), and limited Content-Type/Idempotency-Key header templates. Placeholders use ${fieldName}; required string parameters must be declared. Arbitrary authorization headers and upstream URL configuration are intentionally absent. Each request freezes template revision, environment, school (required for SCHOOL), payload and reason. L1 requests require L2 review; L2's own submissions auto-approve. Only the owner can cancel pending requests; optimistic version checks and row locks prevent conflicting decisions. Legacy GET list routes retain their 100-row cap; paginated POST search routes are preferred. Approval is not execution. Only the separately configured global catalog adapter can dispatch. School-specific execution and centralized audit delivery remain pending.

## Operator management and execution boundary

L2-only operator creation, listing, disable and activation are available under /internal/protected/operators. Initial passwords are supplied by the administrator; secure invitation and forced first-password change are not implemented. Disabling or reactivating revokes sessions; self-disable and removal of the last active L2 are prohibited. No password hashes are exposed. All mutations have workflow event records.

Migration 3 adds executions. POST /internal/protected/requests/{id}/execute requires the approved request version and owner or L2; GET /internal/protected/requests/{id}/execution returns status metadata. Exact environment code and immutable template ID select a deployment-owned adapter. An optional provider-catalog adapter is registered only when all five INTERNAL_TOOL_CATALOG/PLATFORM/WORKLOAD settings are configured. Without a matching binding, requests fail closed with EXECUTION_UNAVAILABLE and create no execution record. No arbitrary HTTP transport is available; only a separate catalog-read scope is supported. The engine resolves restricted path/header placeholders with a conservative segment allowlist, claims once with a database unique constraint and records results. Unknown transport outcomes and abandoned RUNNING claims are never automatically retried; L2 reconciliation records evidence without retrying or rewriting known outcomes. Response bodies are not stored. The catalog adapter is opt-in; no live deployment has been verified.

### First live adapter (opt-in)

Register an environment and an immutable GLOBAL template with method GET, module integrations, endpoint /integrations/restricted/providers, empty headers and bodySchema. Submit with input {} and schoolId null. Set INTERNAL_TOOL_CATALOG_ENVIRONMENT to the environment code and INTERNAL_TOOL_CATALOG_TEMPLATE_ID to the exact template revision UUID; configure the fixed Platform origin, independent Ed25519 key ID/private key and matching Platform InternalToolKeys public key. Run make generate-clients before builds. The consumer uses the provider-owned Integration SDK. Execution stores HTTP status and outcome, not the catalog response body. No school-level operation is bound; no School session, tenant assertion or synthetic system user is accepted. Keep all settings empty until credentials are provisioned. No production environment has been configured by this change.

Bulk approval is available at POST /internal/protected/approvals/bulk-approve with items [{id,version}] and optional comment. Only active L2 operators may approve up to 50 distinct pending requests in one transaction; any stale version, missing request or invalid state rolls back every decision and event. No automatic execution follows approval.

## Search, validation and reconciliation

POST /internal/protected/{environments,api-templates,requests,approvals,operators,workflow-events}/search accepts {pageNumber,rowSize} (defaults 1 and 25, maximum page 10000 and row size 100). Returns records, pageNumber, rowSize and hasMore; no total count or stable snapshot guarantee. Requests remain owner-scoped; approval inbox, operator search and event history require L2. POST searches require session-bound CSRF. Nested fields support properties, items and nullable; schema depth is bounded, unknown and duplicate payload keys are rejected, and placeholders must be required non-null strings. This is not full JSON Schema.

Migration 4 adds execution_reconciliations. POST /internal/protected/requests/{id}/reconcile accepts outcome CONFIRMED_SUCCEEDED, CONFIRMED_FAILED or UNRESOLVED and mandatory evidence, only from L2. UNKNOWN executions or RUNNING claims older than five minutes can be reviewed once. A stale RUNNING claim is marked UNKNOWN; a separate immutable review preserves the original uncertain status and does not enable redispatch. GET /internal/protected/requests/{id}/reconciliation exposes the review only to owner or L2. Workflow event search is local history; central Platform Audit transport is not implemented.

The deployed internal-tool executable accepts `migrate` and `bootstrap EMAIL` (password on stdin) without starting HTTP. The standalone operator-admin command remains a development-compatible entrypoint to the same implementation.

## Centralized operator audit delivery

Migration 5 captures every existing and future workflow event into a durable local audit outbox using a transaction-bound database trigger. Configure all three INTERNAL_TOOL_AUDIT_* settings and a matching dedicated Platform OperatorAuditKeys public key to enable the SDK-based relay. Empty settings retain pending local events without sending them. Delivery uses stable occurrence UUIDs, at-least-once attempts, row locks, five-second request deadlines and 30-second retry delays. Only HTTP 204 marks delivery. HTTP 400/409 blocks an occurrence for operator investigation; other failures retry. The Audit service writes a separate immutable operator_activities table and accepts identical retries, never treating operator UUIDs as School accounts. No request bodies, passwords, comments or evidence are forwarded. This covers existing workflow events, not every auth/read attempt. Global audit search, backlog alerting, retention and end-to-end deployed verification remain pending. The global ingestion path writes directly to the owning Audit database via its restricted endpoint rather than republishing to JetStream; existing tenant event consumers are unchanged.

L2-only centralized operator history is available at POST /internal/protected/operator-activities/search when the separate INTERNAL_TOOL_AUDIT_READ_* credential is configured. Local delivery summary GET /internal/protected/audit-delivery/summary and blocked rows POST /internal/protected/audit-blocked/search work even if delivery is disabled. POST /internal/protected/audit-blocked/{id}/retry requeues the same immutable event after an explicit L2 action, preserving attempts and recording AUDIT_DELIVERY_REQUEUED. Correct upstream configuration or investigate conflicts before retrying. Central search does not include School activity or undelivered events; local workflow history remains authoritative for pending delivery. No automatic resolution of conflicts or alerting is configured.

Migration 6 records bootstrap and successful login/logout occurrences atomically with operator/session changes, and anonymous rejected/rate-limited login counts per hour. Counters are best effort; invalid origin/CSRF requests, failed session checks and per-attempt attribution are not captured. Request ingress generates a new X-Request-ID rather than trusting client-provided IDs. Transactional occurrences carry that UUID through the Audit SDK and centralized storage; previous records have null correlation. This traces Internal Tool actions and their audit delivery, not arbitrary School-to-Platform requests. Cross-service causation and counter retention remain pending. Deploy the Platform Audit correlation migration first, followed by Internal Tool migration 6.

The L2 delivery summary includes a HEALTHY/DEGRADED/DISABLED status and anonymous rejected/rate-limited login counts over the current and previous 23 hourly buckets. GET /health/audit-delivery is a private 204/503 probe, returning 503 for disabled delivery, any blocked occurrence, a pending event aged at least five minutes or a probe error. It is not part of general readiness. Configure monitoring to scrape this endpoint only when delivery is expected; no external notifications or automated requeue are provisioned. The five-minute threshold is an initial policy, not an SLA. Authentication counters are local and require retention planning.

## School-specific execution (read-only pilot)

The first school binding supports GET /audit/restricted/schools/${schoolId}/activity-check (module audit, scope SCHOOL, required string field schoolId, no headers). Set every INTERNAL_TOOL_SCHOOL_* variable to bind one immutable template revision, logical environment, canonical school UUID and comma-separated operator UUID allowlist. The selected school ID and approved input schoolId must match the deployment grant exactly; requester, reviewer and executor must all be allowed. Authorization is evaluated before claiming execution. Global bindings cannot dispatch SCHOOL requests. The Platform key is independently configured with issuer internal-tool-school, subject internal-tool-school:<school UUID>, scope internal.audit.school.activity-check, no delegation; it is never a School session. A 204 indicates recorded tenant audit activity; a 404 means no recorded activity, not proof the school does not exist. Only HTTP status is persisted. Server errors are UNKNOWN and never automatically replayed. The current launcher supports one school binding; the policy map supports additional deployment-owned bindings later. The registry still permits unbound proposals and approvals, but they cannot execute. All school mutations remain denied, even if approved. Non-UUID tenant identifiers are not supported by this pilot; no tenant directory or identifier translation has been implemented. No live credentials or deployment are configured.

### Multiple school grants

INTERNAL_TOOL_SCHOOL_GRANTS accepts a deployment-owned JSON array (max 100 entries), each with environmentCode, templateId, schoolId, operation (currently audit.activity-check only), origin, keyId, privateKey, requesters, reviewers and executors (UUID arrays). Every binding uses an independent credential; duplicate binding keys, reused credentials, invalid roles and mixed legacy/new configuration fail startup. All school grants in one process currently target one Platform origin. The older single-school settings remain supported. The authenticated GET /internal/protected/school-grants endpoint lists only the caller's assigned capabilities, not keys or other operators. This is a configured grant catalog, not a verified school directory. A school mutation proposal cannot self-approve or be self-approved through bulk approval, but independent approval alone does not enable mutation execution. Claiming a school execution rechecks and locks the active requester, reviewer and executor rows within the transaction. Role grants are enforced before dispatch; unbound proposals are still permitted. No mutation SDK or provider-side mutation permission is enabled. Do not commit credentials to source control.

For an explicitly configured school binding, submission validates the requester and exact invocation; L2 automatic approval also requires the reviewer grant. Single and bulk approval validate the configured reviewer grant before the repository transaction. The immutable target and deployment-owned grant are checked again at execution. Unbound proposals still follow registry workflows, but cannot dispatch. Rejection/cancellation behavior is unchanged.

GET /internal/protected/requests/{id}/capabilities reports available actions for the current request version using existing request visibility, school approval grants, resolved invocation and execution bindings. The UI checks this snapshot before presenting individual actions. It is advisory: mutation handlers repeat authorization, live operator checks and version/claim validation. Reconciliation of RUNNING executions still requires the stale cutoff; bulk approval is checked transactionally by the backend. An L1 executor must also own the request under the existing visibility policy; separate non-owner L1 executor queues are not implemented.
