# School backend

Owns browser-facing School and Identity use-case APIs. Platform calls use the restricted authenticated generated SDK clients. No direct Platform database access.

Startup requires SCHOOL_DATABASE_URL for a separately provisioned PostgreSQL database and least-privilege role. No fallback to DATABASE_URL or other project credentials. GET /health/database checks only the owned database; /health/ready checks the owned database and Platform /ready after successful local configuration validation; workload grant and browser verification are separate. School registry migration version 5 is required before startup.

## School registry

The School project owns the authoritative UUID, code, name and lifecycle status. Run `make migrate` before startup, then `go run -mod=mod ./cmd/school register-school UUID CODE "School name"` against the owned database. Registration is idempotent for the same UUID/code/name; conflicting records are rejected. Use the existing canonical tenant UUID when provisioning; there is no automatic Identity tenant creation or translation. Only the deployment operator can provision records in this phase. No rename or disable command is exposed yet.

The School-owned OpenAPI contract is in services/registry/internal/resources/api/openapi/v1/openapi.yaml. POST /school/restricted/registry/lookup is a private, signed workload API. Configure SCHOOL_REGISTRY_READ_GRANTS as a JSON array of objects containing key (WorkloadKeyConfig with public key only) and schoolIds (allowed UUID array). Each key has issuer internal-tool-school-directory, subject internal-tool-school-directory:<reader UUID>, one scope internal.school.registry.read and no delegation; audience school. Every requested school must be authorized before the query runs. Missing rows are omitted. No public enumeration, cross-project database access, browser credential forwarding or mutation API is available.

## School name mutation

Migration 2 adds immutable school_registry.rename_events. Configure SCHOOL_REGISTRY_RENAME_KEYS as a JSON array of independent WorkloadKeyConfig public keys with issuer internal-tool-school-rename, subject internal-tool-school-rename:<school UUID>, only internal.school.registry.rename and no delegation. PATCH /school/restricted/registry/schools/{schoolId}/name accepts expectedName and name plus the execution UUID in Idempotency-Key. New writes require ACTIVE status and the exact current name; identical committed retries return 204 without modifying the current name. Conflicting retries return 409. The local audit receipt is written in the same transaction. This is name-only mutation; no school status, deletion, tenant creation or code changes are enabled. Local receipts do not yet replicate to centralized Audit.

Migration 3 adds a monotonic school version, incremented on name, code or status changes, and a previous_version on new rename receipts. Rename now requires expectedVersion (positive int64) along with expectedName. Pre-version receipts remain immutable and cannot be replayed under the new versioned contract. Development rename templates must be registered as a new revision with required integer expectedVersion.

Migration 4 atomically enqueues versioned rename receipts in rename_outbox, backfilling versioned history. Pre-version receipts stay local. Set all SCHOOL_RECEIPT_* variables to enable the single-school relay; configure the matching independent public key in Platform SchoolReceiptKeys, issuer school-registry-audit, subject school-registry-audit:<school UUID>, audience platform, scope internal.audit.school.rename-receipt.write. Only the configured school's receipts are dispatched; others remain pending. The central receipt stores execution UUID (causation), school UUID, previous version, original timestamp and optional correlation ID, not the old/new names. Identical receipt delivery is acknowledged once durably persisted; transport/temporary errors retry after 30 seconds, 400/409 blocks for investigation. Empty configuration retains pending receipts locally. No external alerting or receipt management UI is provisioned. Deploy Audit migration before School migration 4. Rename SDK propagates the Internal Tool request correlation ID; older receipts may lack one.

### Multi-school receipt delivery

Use SCHOOL_RECEIPT_PUBLISHERS instead of the legacy single-school settings for a JSON array of up to 100 objects containing origin, schoolId, keyId and privateKey. Each school requires a distinct matching Platform SchoolReceiptKeys entry. Duplicate school IDs and reused key IDs/public keys (including the School outbound workload, directory readers and rename credentials) are rejected before launch. Four round-robin shards bound concurrent delivery and each worker reads only its assigned school. No credential or event content is logged. GET /health/audit-delivery is a private aggregate 204/503 probe, independent of normal readiness. It returns 503 for disabled configuration, any blocked or unconfigured pending receipt, any pending receipt at least five minutes old or a database error. External alerting is not configured. This probe covers rename receipts only.

Migration 5 adds immutable status_events. PATCH /school/restricted/registry/schools/{schoolId}/status requires an independent per-school public key (SCHOOL_REGISTRY_STATUS_KEYS, issuer internal-tool-school-status, subject internal-tool-school-status:<school UUID>, scope internal.school.registry.status, no delegation). Expected status and version must match the locked row, and ACTIVE↔DISABLED changes increment the existing school version. Execution UUIDs cannot be reused across rename and status operations. Registry status is not a complete access suspension: existing Identity sessions and School business endpoints are unchanged. Status receipts stay local pending a centralized status receipt contract and relay.

Migration 6 adds status_outbox with transactional enqueue and backfill of status_events. SCHOOL_RECEIPT_PUBLISHERS entries now accept operation (rename default, or status). Each school/operation pair requires a separate credential. Status publishers use school-registry-status-audit:<school UUID>, issuer school-registry-status-audit, audience platform, scope internal.audit.school.status-receipt.write. Both mutation types share the four-shard scheduler and health probe. Missing publishers, blocked events and aged pending events degrade health. Status receipts include ACTIVATE or DISABLE, not user details. Legacy single-school configuration remains rename-only.

Platform tenant access verification: configure SCHOOL_REGISTRY_ACCESS_KEYS with independent public keys for issuer and subject platform-tenant-access, scope platform.school.access-check, audience school. GET /school/restricted/registry/schools/{schoolId}/access-check is a status-only private API (204 for ACTIVE, 403 for missing/disabled/unauthorized, 503 for database failure). The credential can check any registry UUID but cannot enumerate or retrieve names or change state. Keep this route outside browser ingress.
