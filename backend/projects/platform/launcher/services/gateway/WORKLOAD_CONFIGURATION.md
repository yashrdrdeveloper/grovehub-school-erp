# Platform workload configuration

Set PLATFORM_WORKLOAD_CONFIG to a JSON object with Keys and Routes. Each key has KeyID, PublicKey (unpadded base64url Ed25519), Issuer, Subject, Scopes and AllowDelegation. Routes maps exact method + restricted route template to Scope and RequireActor. Audience is platform. Empty configuration denies workload calls except the separately verified Gmail webhook.

The provider-owned restrictedPolicies table is authoritative: configured routes must match its exact scope and actor requirement. A configuration may omit a route to disable it. One signed scope is accepted per request. Login and forgot-password use only the school workload; refresh, recovery and setup use route-specific proofs validated by their controllers. Other Identity operations and Audit require live access-proof verification and protected-route authorization. Integration business operations require live access-proof verification; controllers enforce tenant, ownership and system-mail admin rules. OAuth callback uses the school workload and one-time state, not a browser credential.

Foundation uses the separate school-foundation subject and explicit foundation.persons.create/get/update/search/deactivate scopes; no School browser wrapper or ordinary school workload is allowed. Gmail push cannot be configured as a school workload operation.

School constructs separate Identity, Audit and Integration HTTP clients, each restricted to its own operation policy. For development these clients share the existing School signing identity and key; this is client-side policy isolation, not independent cryptographic identities. Keep private keys in consumers. Existing environment configuration must use the canonical scopes in the table. Do not deploy until full application verification passes.

## Internal Tool catalog access

Optional InternalToolKeys in PLATFORM_WORKLOAD_CONFIG is a separate list of public keys. Each must have Issuer and Subject equal to internal-tool, AllowDelegation=false, and exactly one scope internal.integration.catalog.read. Key IDs and public keys may not overlap School keys. It authorizes only GET /integrations/restricted/providers, without cookies, identity proof, actor claims or query parameters. The existing School route policy still requires live actor authorization. No tenant-specific operations or mutations are enabled. Configure keys separately for each Platform environment.

OperatorAuditKeys is a separate optional key list. Each issuer and subject must be internal-tool-audit, exactly one scope internal.audit.operator.write, no delegation, and independent key IDs and public keys from School and catalog keys. It grants only POST /audit/restricted/operator-activities. No tenant, School session or actor claim is accepted; the operator identity is an assertion made by the authenticated Internal Tool audit publisher. Records are isolated from tenant search. No generic execution access is granted.

OperatorAuditReadKeys optionally grants only POST /audit/restricted/operator-activities/search. Issuer/subject internal-tool-audit-reader, exactly one scope internal.audit.operator.read, no delegation. Keys must be independent from School, catalog and operator writer keys. The Internal Tool protected wrapper must check the live L2 operator session before using this credential. Neither operator credential can access School tenant search.

SchoolExecutionKeys grants only GET /audit/restricted/schools/{schoolId}/activity-check. Issuer internal-tool-school, subject internal-tool-school:<canonical-school-uuid>, exactly one scope internal.audit.school.activity-check, no delegation. Each key is independent of every other key including those for other schools. The provider checks the signed subject against the exact school path before accessing tenant data. This is a read-only activity-existence check, not a general-purpose school principal or mutation grant.

SchoolReceiptReadKeys grants only POST /audit/restricted/school-rename-receipts/search. Issuer and subject internal-tool-school-receipt-reader, scope internal.audit.school.rename-receipt.read, no delegation, independent key. Global L2 metadata visibility is intentional and separate from operator history, School tenant history and receipt publishing. The wrapper verifies the live L2 session. No old/new names are returned.

SchoolStatusReceiptKeys grants only POST /audit/restricted/school-status-receipts using issuer school-registry-status-audit, subject school-registry-status-audit:<school UUID>, scope internal.audit.school.status-receipt.write and a distinct key. The prior rename publisher grant stays rename-only. Replace the receipt reader scope with internal.audit.school.mutation-receipt.read and the search route with POST /audit/restricted/school-mutation-receipts/search to explicitly authorize global lifecycle and rename metadata. Old reader grants no longer work.

Tenant session reconciliation uses the existing signed Platform-to-School access-check credential. A known disabled school returns 403 with its current generation; an unknown school, invalid credential or unavailable registry never supplies a usable generation. The authentication adapter accepts only active responses. Identity scans tenants with unexpired, unrevoked sessions in bounded batches, revokes only rows strictly older than the authoritative generation, and retries failed lookups or writes on subsequent sweeps. No new workload grant, shared database or delivery queue is required. Revocation is idempotent and cannot revoke a newer session after a delayed response. Configure both projects and apply their migrations before enabling the access policy. Existing generation-zero sessions are revoked by reconciliation. Expired sessions need no access revocation. Session lists filter to the authenticated generation before pagination.

Recovery and setup proofs are bound to the same registry generation at issuance. Exchanging a proof copies its original generation, not a later registry value. Existing generation-zero proofs require reissuance when the registry policy is enabled. The Identity invitation worker receives the same signed state lookup at startup: stale or disabled-school mail is suppressed, while an unavailable registry leaves the job retryable after its lease expires. The registry check precedes mail transport; already accepted or in-flight provider deliveries cannot be recalled.
